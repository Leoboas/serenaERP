# Security posture and operating rules

## Scope

This document describes protections present in the repository and the
boundaries they do not cover. It is not a certification, a penetration-test
report, or evidence that a Terraform configuration has been applied to an AWS
account.

## Static repository check

The current working-tree review used:

~~~bash
git ls-files
git check-ignore --verbose .env
rg -l --hidden -g '!.git/**' -g '!.venv/**' \
  'AKIA[0-9A-Z]{16}|ASIA[0-9A-Z]{16}|-----BEGIN .*PRIVATE KEY-----|aws_secret_access_key'
~~~

The tracked-file listing contains .env.example but not a real .env, virtual
environment, pytest cache, local database, log directory, or Terraform state.
The focused scan did not identify a high-confidence AWS access key, private
key, or AWS secret-access-key assignment in source files. The gitignore and
dockerignore exclude environment files, local state, logs, databases and common
key/certificate extensions.

This is evidence about the visible working tree only. It does not scan Git
history, CI secrets, developer home directories, image registries, cloud
accounts, or third-party logs. Run a history-aware secret scanner in CI before
public release and rotate any credential if a real value is ever committed.

Local Compose credentials such as goverp/goverp and the development tenant are
publicly known test values. They must never be copied to a shared or production
environment.

## Authentication and authorization

### Cognito JWT validation

Outside development, the verifier:

1. Retrieves signing keys from the configured Cognito JWKS endpoint with a
   finite HTTP timeout and cache.
2. Verifies RS256 signature and issuer.
3. Checks token_use against COGNITO_TOKEN_USE.
4. Checks the relevant audience/client ID.
5. Requires custom:tenant_id.

Terraform configures COGNITO_TOKEN_USE as id because Cognito ID tokens contain
the immutable custom tenant attribute without requiring a pre-token Lambda.
The user pool client cannot write custom:tenant_id and self-registration is
disabled; an administrative provisioning workflow assigns the tenant.

The API must treat a valid JWT as authentication, not authorization. The tenant
claim is compared to X-Tenant-ID on every tenant-aware HTTP request. A missing
or mismatched header is rejected before application use cases run.

### Development bypass

Bearer dev-token is accepted only when ENVIRONMENT is exactly development. The
application default is production, so an omitted environment does not enable
the bypass. Compose opts into development explicitly. Never set
ENVIRONMENT=development on a shared, staging, or production deployment.

## Tenant data isolation

The active control stack is:

| Layer | Protection |
| --- | --- |
| HTTP | Token claim must equal X-Tenant-ID. |
| Domain | TenantId makes tenant ownership explicit in entities and ports. |
| Repository | Reads and state-changing operations use tenant_id predicates. |
| Jobs | Messages and durable jobs include tenant_id; claims and state changes verify it. |
| Database | Foreign keys, unique business key per tenant, and composite FK from analysis job to licitação. |
| Tests | Cross-tenant read and analysis-trigger attempts are negative tests. |

PostgreSQL Row Level Security is not enabled. It is a recommended defense in
depth only after a deliberate design for request-scoped database identity,
background workers, migrations, support access, and connection pooling. Do not
enable it ad hoc: an incorrectly set or leaked session variable can create a
new cross-tenant failure mode.

## Secrets and configuration

Runtime credentials are configuration, not source:

- Local settings load from .env, which is ignored.
- ECS injects database, Redis and Cognito configuration through Secrets
  Manager references.
- The ECS execution role has Secrets Manager read permission only for the
  configured secret ARNs and KMS decrypt constrained through Secrets Manager.
- RDS and ElastiCache passwords are generated by Terraform rather than hard
  coded.

Important remaining risk: Terraform state contains sensitive generated values.
The repository declares an S3 backend and provides backend.hcl.example, but it
cannot create or select the organization-controlled bucket, lock table, KMS
policy and restricted IAM access from the workload state itself. Before an AWS
apply, copy the template to ignored backend.hcl, provision that bootstrap
backend, initialize it deliberately, and keep local state out of shared folders
and logs. This requires a real AWS account and backend ownership decision.

## Network and transport

The Terraform target is:

- ECS tasks in private subnets without public IPs;
- an ALB that redirects port 80 to a required TLS listener on 443;
- RDS and ElastiCache in private subnets;
- database and Redis ingress limited to the ECS service security group;
- RDS storage encryption, backups and forced TLS;
- ElastiCache transit encryption, at-rest encryption and AUTH token.

This does not establish egress filtering: ECS service security-group egress is
currently broad. Network ACLs, VPC endpoints, DNS controls, WAF policy, flow
logs and threat-detection configuration are not yet present in this repository.

## Containers and supply chain

The runtime stage creates and uses a non-root serena account. A plain docker
build now ends at the production stage; CI builds the runtime target
explicitly. Docker Compose opts into the development target only for the local
API test runner, while migration, worker and Beat use the runtime target.

For a production image, use:

~~~bash
docker build --target runtime --tag registry.example/serenaerp:VERSION .
~~~

Dependencies are version-bounded but not lock-file pinned; add a reviewed lock
process and vulnerability scanning before release.

## Logging, privacy and incident evidence

Critical API/worker events can carry request correlation ID, job ID, tenant ID
and retry count. Do not log:

- Authorization headers, JWTs, client secrets, Redis URLs with credentials, or
  database URLs with passwords;
- procurement documents or personal data unless retention and access controls
  are approved;
- full exception payloads from external AI providers if they can include user
  or procurement content.

When collecting an incident bundle, retain timestamps, correlation IDs, job
IDs, container/task IDs and sanitized error type. Redact values before placing
logs in tickets or chat.

## Release security gate

Before an internet-facing deployment, require evidence for all of the following:

1. Current tests, lint and Alembic head check pass in CI.
2. A real PostgreSQL/Redis/Celery smoke run covers tenant A versus tenant B,
   broker failure/recovery, and duplicate job delivery.
3. A secret scan covers both current content and Git history.
4. A reviewed Terraform plan confirms no unexpected replacement or public data
   path.
5. ACM certificate, DNS, remote encrypted Terraform backend, least-privilege
   deploy role, logging retention and alarms are configured in the target
   account.
6. Cognito administrative provisioning and, where required by policy, MFA and
   recovery controls are tested with real tokens.

## Reporting a vulnerability

Do not disclose exploitable details in a public issue before maintainers have
assessed the impact. Use the repository owner's approved private reporting
channel and include reproduction steps, affected version/commit, impact and
sanitized evidence. If no private channel is published, ask the repository
owner to establish one before public launch.
